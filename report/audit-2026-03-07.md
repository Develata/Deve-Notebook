## 1. Critical

### C1. `repo_id` 仍未成为端到端的权威主键，新的 WebLightPeer 设计没有真正落地
**计划要求**
- `deve-note plan/05_network.md:22-27`、`45-63`、`95-106`
- `deve-note plan/04_storage.md:186-202`
- 这些文档现在都要求：浏览器 identity / vector / cache 严格按真实 `repo_id`（UUID）分桶，并以 `repo_id` 做同步路由主键。

**当前实现**
- 前端存储运行时仍按仓库名或默认字符串建桶，而不是按 UUID：`apps/web/src/hooks/use_core/storage_runtime.rs:16-19`、`51-58`
- 初始没有 repo 时直接落到 `"default"`，并立即尝试恢复/生成 identity：`apps/web/src/hooks/use_core/storage_runtime.rs:16-19`、`51-83`
- 服务端发给前端的 `RepoSwitched` 仍然把 `uuid` 留空：`apps/cli/src/server/handlers/listing.rs:29-33`
- 前端握手时把 `identity.repo_id` 当 UUID 解析，失败后直接回退 `Uuid::nil()`：`apps/web/src/hooks/use_core/effects.rs:91-99`
- 前端收到服务端 `SyncHello` 后保存 vector 时仍按 `current_repo` 名称写回，而不是按协议中的真实 repo UUID：`apps/web/src/hooks/use_core/effects.rs:169-180`
- 服务端仍保留 `get_repo_id()->Uuid::nil()` 的兜底：`apps/cli/src/server/handlers/mod.rs:20-30`
- 文件树状态仍是进程级共享对象；Watcher 把本地 repo 的 `TreeUpdate` 广播给所有连接，没有 repo 过滤：`apps/cli/src/server/mod.rs:52-64`、`apps/cli/src/server/setup.rs:95-117`、`apps/web/src/hooks/use_core/effects.rs:233-235`

**问题**
- 新 plan 已经从“仓库名/默认仓库”升级到“真实 `repo_id` + repo-scoped identity”，但运行时代码仍有一半逻辑停留在旧模型。
- 现在浏览器身份桶、握手路由、vector 持久化、TreeUpdate 广播都没有建立在同一个权威 `repo_id` 上。
- 这不是文档小漂移，而是“模型已改，核心路径没跟上”。

**风险**
- 浏览器可能为 `"default"` 或仓库名生成错误身份，并把首次握手发到 `Uuid::nil()`。
- 多 repo / 多 tab / 本地与影子分支并存时，identity、vector、树状态会交叉污染。
- 后续所有同步正确性、权限校验和灾难恢复都无法建立在可靠 repo 路由上。

**建议**
- 前端必须等待服务端给出真实 repo UUID 后再初始化 repo-scoped identity；禁止 `"default"`/仓库名冒充 `repo_id`。
- `RepoSwitched`、`ListRepos`、`SyncHello`、`SyncAck`、TreeUpdate 广播都统一到真实 `repo_id`。
- 进程级 `tree_manager` 与广播消息至少要按 repo 过滤，否则 repo 隔离在 UI 层仍是假的。

## 2. High

### H1. 同步连接没有真正绑定“已认证 peer + 已选 repo”，`SyncPush` 甚至被写入 `unknown` 分支
**证据**
- Plan 要求握手后把连接绑定到单个 repo，并拒绝后续跨 repo 消息：`deve-note plan/05_network.md:99-106`
- `WsSession` 明明预留了 `authenticated_peer_id`，但仓库里没有任何地方调用 `set_authenticated()`：`apps/cli/src/server/session.rs:20-24`、`52-53`
- `handle_sync_hello` 根本不接收 `session`，因此握手结果不会写入会话态：`apps/cli/src/server/ws/route/mod.rs:16-34`、`apps/cli/src/server/handlers/sync.rs:16-25`
- `handle_sync_request` / `handle_sync_push` 只信任消息自带的 `repo_id`，不校验是否和已握手 repo 一致：`apps/cli/src/server/handlers/sync.rs:108-173`
- 增量 `SyncPush` 直接把来源 peer 写成 `PeerId::new("unknown")`：`apps/cli/src/server/handlers/sync.rs:158-163`
- Core 同步引擎会把该 `peer_id` 写入影子库与向量时钟：`crates/core/src/sync/engine/transfer/apply.rs:40-57`

**问题**
- 当前连接既没有“这个连接已经认证成谁”，也没有“这个连接被锁定在哪个 repo”。
- 一旦客户端发 `SyncPush`，服务端会把远端操作记到 `unknown` 分支，而不是握手过的 peer。
- 这和文档定义的 trust registration / deterministic routing 是正面冲突。

**风险**
- 影子库归属错误，向量时钟归属错误，后续合并/审计都失真。
- 一个已登录连接可以在握手后继续向别的 `repo_id` 推送数据，服务端没有拒绝机制。

**建议**
- `SyncHello` 成功后把 `authenticated_peer_id` 与 `bound_repo_id` 写入 `WsSession`。
- 后续 `SyncRequest` / `SyncPush` / `SyncSnapshotRequest` / `SyncPushSnapshot` 全部校验与会话绑定一致。
- 增量 `SyncPush` 禁止再用 `"unknown"`；来源必须来自握手后的会话态。

### H2. 快照同步与手动合并路径仍大量绕过真实 repo 身份
**证据**
- `get_snapshot_for_sync()` 明写“`request.repo_id` 仅用于回包标识”，实际始终从本地主仓库取数据：`crates/core/src/sync/engine/transfer/snapshot.rs:13-21`
- 手动同步模式的 `GetSyncMode` / `SetSyncMode` / `GetPendingOps` / `ConfirmMerge` / `DiscardPending` 仍全部用 `Uuid::nil()` 取 SyncEngine：`apps/cli/src/server/handlers/merge.rs:14-138`
- Core 与工具链仍保留若干本地 repo `Uuid::nil()` 快捷路径：`crates/core/src/vfs.rs:89`、`crates/core/src/sync/handler.rs:127-130`、`crates/core/src/ledger/manager/ops_ops.rs:50-53`

**问题**
- 即使前面的握手层补上 repo 绑定，快照与手动合并路径仍然可能落到错误 repo。
- 这说明“多 repo 支持”在协议层已存在，但在实际执行层仍没完全生效。

**风险**
- 快照回退、待合并操作统计、手动确认合并都可能读写错仓库。
- 多 repo 下会出现“握手看似正确，实际操作落错库”的更隐蔽故障。

**建议**
- `SyncSnapshotRequest` 必须按请求 `repo_id` 取快照，不能再默认为主仓库。
- 合并与同步模式查询必须接收真实 repo 上下文，禁止 `Uuid::nil()` 进入运行态。

### H3. 认证契约仍会在 debug 构建中静默降级到开发凭据，且绕过显式 localhost 开关
**证据**
- Plan 规定：缺少认证环境变量时应 fail-closed；安全策略分支由 `DEVE_ENV` 与显式配置决定：`deve-note plan/09_auth.md:5-6`、`91-99`、`157-166`
- `AuthConfig::from_env()` 只要是 debug 构建就自动 `dev_default()`，即使 `DEVE_ENV` 未设置：`crates/core/src/security/auth/config.rs:31-49`
- `dev_default()` 仍是固定密钥 + `admin/admin` + `allow_anonymous_localhost=true`：`crates/core/src/security/auth/config.rs:80-89`
- `router::load_auth_config()` 还会把这种行为记录成正常“Development mode with default credentials”：`apps/cli/src/server/router.rs:68-89`
- 服务默认绑定 `0.0.0.0`：`apps/cli/src/server/mod.rs:163-167`

**问题**
- 文档已经把“显式开发模式”与“显式 localhost 免密开关”写清楚，但代码仍把“debug 构建”当作隐式授权。
- 这会把安全基线从“配置驱动”退回“编译模式驱动”。

**风险**
- 调试版误部署到公网时，服务会在已知凭据下启动。
- `AUTH_ALLOW_ANONYMOUS_LOCALHOST` 的显式开关语义被破坏，因为 debug 模式会直接把它置成真。

**建议**
- 删除 `cfg!(debug_assertions)` 的隐式授权，仅允许 `DEVE_ENV=development` 或显式 CLI 开关进入开发认证模式。
- 若保留开发默认账户，至少要求仅绑定 loopback，而不是 `0.0.0.0`。

### H4. Web 端仍没有完整登录流，开启认证后用户只会看到无限重连遮罩
**证据**
- Plan 要求：未认证访问 Dashboard 必须跳转 Login：`deve-note plan/08_ui_design_01_web.md:66-69`
- `apps/web/src/app.rs:20-27` 仍直接渲染主布局，没有登录路由或鉴权分流
- 仓库中未找到 `/api/auth/login`、登录组件或登录表单调用（全仓 `rg` 结果为空）
- 未连上 WS 时，前端只会显示重连遮罩：`apps/web/src/components/disconnect_overlay.rs:11-33`
- 服务端 `/ws` 与受保护 API 仍要求 JWT：`apps/cli/src/server/router.rs:31-53`、`apps/cli/src/server/ws/mod.rs:23-49`

**问题**
- 当前前端在“有认证要求、但尚未登录”的正常状态下，无法给用户任何可操作入口。
- 这不是体验问题，而是认证功能没有闭环。

**风险**
- 只要启用认证，Web 端就会陷入“不断重连 -> 401/失败 -> 再重连”的死循环。
- 文档中的 Dashboard/Auth 方案在真实部署中不可用。

**建议**
- 前端补齐登录页、`/api/auth/login` 调用、401 处理与未认证重定向。
- DisconnectedOverlay 需要区分“网络断开”和“未登录/401”这两类状态。

### H5. “断连即只读”没有真正封口，离线队列仍会缓存部分写操作并在重连后回放
**证据**
- Plan 要求：断连后 UI 必须立即锁定，禁止任何写操作：`deve-note plan/08_ui_design_01_web.md:63-69`、`95-110`
- 输出管理器自称会阻止写操作，但写消息白名单并不完整：`apps/web/src/api/output.rs:38-42`、`173-194`
- Source Control 仍通过 WS 发送 `Commit` 与 `ResolveConflict`：`apps/web/src/hooks/use_core/callbacks_sc.rs:60-85`
- 这些消息没有被 `is_write_message()` 识别，因此断连时会被加入队列并在重连后发送：`apps/web/src/api/output.rs:62-69`、`115-133`

**问题**
- 现在“断连即只读”只封住了一部分操作，至少 `Commit`、`ResolveConflict`、`DeletePeer`、`SetSyncMode` 仍能绕过。
- 这和输出管理器自己的注释契约也不一致。

**风险**
- 用户在断线期点击的动作会被悄悄缓存，重连后异步执行。
- 对于提交、冲突解决、删除 peer 这类操作，这是明显的行为惊讶和状态污染。

**建议**
- 反向定义：只允许明确的查询类消息离线入队，其余默认阻止。
- 同时在 UI 层禁用提交、冲突解决、删除 peer 等按钮，避免双重失配。

## 3. Medium

### M1. 根路径 `/` 仍不会稳定显示 Dashboard，初次进入会自动打开第一篇文档
**证据**
- Plan 规定：根路径无 DocId 时显示 Dashboard：`deve-note plan/08_ui_design_01_web.md:66-69`
- `handle_doc_list()` 只要当前没文档且 `explicit_home=false`，就自动选中第一篇：`apps/web/src/hooks/use_core/effects_msg.rs:19-34`
- `WsService` 在新连接时还会主动塞一条 `ListDocs`：`apps/web/src/api/output.rs:76-89`

**问题**
- 这意味着初次打开 `/` 时，只要仓库里有文档，Dashboard 很快就会被第一篇文档替代。
- 当前修复只解决了“点击 Home 后不要被抢走”，并没有实现 plan 里的根路由语义。

**建议**
- 把“当前页面=Dashboard”与“当前选中文档=None”彻底解耦。
- 初次进入根路径时，不应把 `DocList` 当成“自动打开第一篇”的触发器。

### M2. 速率限制策略与文档不一致，尤其缺少 WebSocket 消息级限流
**证据**
- Plan 要求：`POST /api/auth/login` 5 次/分钟/IP，API 120 次/分钟/IP，WebSocket 200 条消息/分钟/连接：`deve-note plan/09_auth.md:131-136`
- 路由层实际只挂了一个 200 次/分钟/IP 的全局中间件：`apps/cli/src/server/router.rs:28-29`
- 具体实现也是统一 per-IP 窗口，没有 endpoint 粒度：`apps/cli/src/server/rate_limit.rs:46-121`
- WebSocket 消息循环里没有任何消息级限流：`apps/cli/src/server/ws/mod.rs:87-120`

**问题**
- 当前实现只能挡住“HTTP 请求过快”，挡不住“单个已建立 WS 连接高频灌消息”。
- 文档里的三层限流策略目前只实现了一小部分。

**建议**
- 登录、普通 API、WS 消息分别限流，不要混成一个总桶。
- 至少给 WebSocket 消息路由加每连接计数器，否则 `200 条/分钟/连接` 只是文档承诺。

### M3. 主计划、验收用例与代码现状仍有系统性漂移
**证据**
- 总索引仍写着 `Ready for Implementation`：`deve-note plan/deve-note plan.md:5`
- 网络文档仍写“Client-Server 使用 JSON”，但服务端单播已经是 Bincode：`deve-note plan/05_network.md:78`、`apps/cli/src/server/ws/send.rs:19-42`

- 代码注释仍引用不存在的 `03_ui_architecture.md`：`apps/web/src/components/spectator_overlay.rs:5`、`apps/web/src/components/quick_open/mod.rs:5`

**问题**

- 新协作者会被旧端口、旧端点、旧章节名误导。

**建议**

- 删除失效文档引用，避免继续传播旧架构名称。

## 5. 建议优先级
1. 先修 `C1 + H1 + H2`，把 `repo_id`、握手绑定、快照/合并路由打通，否则多仓库与 WebLightPeer 都建立在错误主键上。
2. 再修 `H3 + H4`，把认证模式切回显式配置驱动，并补齐前端登录闭环。
3. 接着修 `H5 + M2`，封住断连写入回放与 WS 消息限流缺口。
4. 最后处理 `M1 + M3 + M4`，把 Dashboard 语义、验收文档与模块边界重新拉齐。
