## 1. Critical

### C1. 认证配置在缺省环境下会自动退回公开开发凭据
**证据**
- `apps/cli/src/server/router.rs:69-80` 在 `AUTH_SECRET`/`AUTH_PASS` 缺失时直接回退到 `dev_default()`
- `crates/core/src/security/auth/config.rs:67-79` 的开发默认值是固定密钥 + `admin/admin` + `allow_anonymous_localhost = true`
- `apps/cli/src/server/mod.rs:162-166` 服务默认绑定 `0.0.0.0`
- `deve-note plan/09_auth.md:5-18` 明确要求 12-Factor Auth，第一次启动即应依赖环境变量
- `deve-note plan/acceptance-cases/08_auth.md:4-11` 甚至仍假设缺少 `AUTH_SECRET` 时会报错或生成随机密钥，而不是直接启用固定开发账户
**问题**
- 这不是“开发便利”，而是运行时安全降级。
- 只要部署时漏配环境变量，服务就会在公网绑定地址上以已知口令启动。
- 文档、验收用例和真实行为已经分叉，团队很容易误判当前安全基线。
**风险**
- 生产误部署后直接暴露默认管理员账户。
- 后续所有 JWT、RepoKey、WebSocket 鉴权都建立在这个错误前提上。
**建议**
- 生产路径改为 fail-closed，缺少认证环境变量时拒绝启动。
- `dev_default()` 只能在显式 `DEVE_ENV=development` 或独立 `--dev-auth` 开关下启用。
- 同步修订 `09_auth.md` 与 `acceptance-cases/08_auth.md`，禁止再把“自动回退开发凭据”写成隐式行为。
## 2. High

### H1. 反向代理 / HTTPS / 登录流与当前实现不闭合
**证据**
- `deve-note plan/09_auth.md:76-80` 设计明确推荐反向代理终止 TLS
- `apps/web/src/api/connection.rs:160-183` Web 前端默认硬编码探测 `3001..3005`，不会优先使用当前页面 origin/port
- `apps/cli/src/server/auth/handlers.rs:143-150` JWT Cookie 固定 `secure(false)`
- `apps/cli/src/server/setup.rs:14-30` CORS 仅允许 `http://localhost:*` 和 `http://127.0.0.1:*`
- `deve-note plan/08_ui_design_01_web.md:66-70` 规定未认证访问应跳转 Login
- 审查 `apps/web/src/` 未发现登录页、登录表单或 `/api/auth/login` 的前端调用逻辑
**问题**
- 通过 Nginx/Caddy 暴露在 `https://example.com` 时，前端仍会强行打到 `wss://example.com:3001/ws`。
- Cookie 未标记 `Secure`，与 `09_auth.md:60` 中的 `Set-Cookie: ... Secure` 不一致。
- CORS 白名单没有配置入口，远程域名部署要靠改代码，不是改配置。
- 后端已引入 JWT，但前端没有完整登录/401 恢复路径，认证流只做了一半。
**风险**
- 公开部署时 Dashboard 无法稳定连接。
- Cookie 在 HTTPS 场景下仍允许降级到明文 HTTP 传输。
- 文档中的“远程 Dashboard + 反代 TLS”目前并非真实可用路径。
**建议**
- WebSocket URL 优先使用当前 origin 的相对路径 `/ws`，只把 `3001..3005` 作为本地开发 fallback。
- Cookie 的 `Secure` 取值改为配置驱动，或根据反代头/环境判断。
- CORS 改为环境变量白名单，而不是硬编码 localhost。
- 前端补齐登录页、401 状态处理和未认证重定向。

### H2. Web 端已经从“无状态面板”漂移成持久化 P2P Peer
**证据**
- `deve-note plan/05_network.md:19-24` 规定 Web 端不是独立 P2P 节点，且应保持 `Stateless / RAM-Only`
- `apps/web/src/hooks/use_core/mod.rs:36-41` 明确把 `IdentityKeyPair` 存进 `localStorage`
- `apps/web/src/hooks/use_core/mod.rs:85-92` 前端启动时加载该身份并建立握手 effect
- `apps/web/src/hooks/use_core/effects.rs:22-60` 连接成功后主动发送 `ClientMessage::SyncHello`
**问题**
- 当前 Web 前端已经具备独立 `PeerId`、公钥、签名与握手行为，这和“只是 Server 面板”的文档定义不一致。
- 持久化的是安全身份状态，不是 UI 偏好，超出了 `05_network.md:23` 的例外范围。
- 更糟的是，浏览器握手时仍发送 `VersionVector::new()`，说明它既被实现成 Peer，又没有真正维护 Peer 状态。
**风险**
- 架构角色模糊，后续同步、审计、权限和恢复策略都会混乱。
- 浏览器端 localStorage 长期保存身份材料，不再是纯 RAM-only 投影。
- 一旦继续沿这条路径扩展，很容易把 Web 面板误做成弱一致 P2P 节点。
**建议**
- 必须二选一。
- 若 Web 端只是 Dashboard，就移除浏览器 `IdentityKeyPair`、`SyncHello`、本地 PeerId 持久化。
- 若 Web 端要成为真正 Peer，就更新 `05_network.md`、重新定义身份、向量时钟、持久化与安全模型。

### H3. 多仓库同步路径仍残留 `Uuid::nil()` 占位与 `repo_id` 忽略
**证据**
- `crates/core/src/sync/engine/handshake.rs:21-22` 仍写着 `TODO: Pass actual RepoId`
- `apps/cli/src/server/handlers/listing.rs:41-43` 和 `apps/cli/src/server/handlers/listing.rs:76-78` 在远端分支文档/节点读取时硬编码 `uuid::Uuid::nil()`
- `crates/core/src/sync/engine/transfer/snapshot.rs:19-21` 注释承认“当前仍以主仓库为来源；request.repo_id 仅用于回包标识”
- `apps/cli/src/server/handlers/merge.rs:119-123` 获取不到 repo info 时仍回退到 `Uuid::nil()`
**问题**
- RepoId 已经在协议、影子库、同步请求里到处存在，但真实运行路径仍经常把它当占位符。
- `get_snapshot_for_sync` 直接忽略请求中的 `repo_id`，意味着快照来源与目标 repo 已脱钩。
**风险**
- 多仓库模式下，增量同步、快照同步和分支合并都可能落到错误 repo。
- `remotes/<peer>/<repo>.redb` 的隔离设计会被运行时代码绕过，进而产生错误覆盖或误读。
**建议**
- 把 `RepoId` 从“可选元数据”提升为所有同步路径的强约束。
- 在 `SyncHello`、`SyncRequest`、`SwitchRepo`、`MergePeer` 的整条链路上禁止 `Uuid::nil()` 进入运行态。
- 为多 repo + remote shadow 增加针对性测试，而不是继续依赖单仓库 happy path。

### H4. 插件权限模型没有真正封口，且缺少运行配额
**证据**
- `deve-note plan/11_plugins.md:36-42` 要求所有 Host Functions 做 Capability 校验，并支持 CPU/Mem/Timeout 配额
- `crates/core/src/plugin/runtime/host/mod.rs:80-88` 无条件注册 `skill`、`search`、`mcp` API
- `crates/core/src/plugin/runtime/host/fs.rs:55-63` 的 `get_project_tree()` 完全不做 Capability 校验
- `crates/core/src/plugin/runtime/host/search.rs:20-40` 的 `search_files` / `grep_files` 也没有权限门禁
- `crates/core/src/plugin/runtime/host/skill.rs:41-78` 允许插件读取多个技能目录内容，同样没有权限声明
- `crates/core/src/plugin/runtime/rhai_v1.rs:40-52` 只设置了表达式深度，没有 `max_operations`、内存上限或超时
**问题**
- Manifest 中虽然定义了 `allow_fs_read`、`allow_net` 等能力，但并未覆盖所有敏感 API。
- 现在的插件隔离更像“部分门禁”，不是 default-deny 沙箱。
- 没有操作数/超时限制，Rhai 脚本可通过无限循环或大搜索直接拖垮进程。
**风险**
- 非信任插件可枚举项目树、grep 仓库、读取 skill 内容，甚至桥接 MCP 工具。
- 单个恶意脚本即可造成 CPU 打满、长时间阻塞或敏感信息外泄。
**建议**
- 先把 `search`、`skill`、`mcp`、`get_project_tree` 全部纳入 Capability 体系。
- 再为 Rhai Runtime 加上 `set_max_operations`、执行超时、输出大小限制。
- 若未来要支持第三方插件，必须先补齐沙箱，再继续扩展 Host API。

### H5. Dashboard 根态无法稳定停留，和设计规格直接冲突
**证据**
- `deve-note plan/08_ui_design_01_web.md:36-70` 规定根路径 `/` 在无文档选择时显示 Dashboard
- `apps/web/src/components/main_layout.rs:108-109` Home 按钮只是把 `current_doc` 设为 `None`
- `apps/web/src/hooks/use_core/effects_msg.rs:24-27` 只要收到 `DocList` 且当前没有文档，就自动选中第一篇文档
- `apps/web/src/api/output.rs:71-72` 新连接建立后会主动把 `ClientMessage::ListDocs` 塞回队列头部
**问题**
- 这意味着用户即使点击 Home 回到 Dashboard，也很容易被后续 `DocList` 拉回第一篇文档。
- 如果仓库里有文档，Dashboard 更像是短暂闪现，而不是稳定页面状态。
**风险**
- Web 端“Server Dashboard”定位被实际交互抹掉。
- 后续接入 metrics、actions、健康检查时，用户路径会非常不稳定。
**建议**
- 把“当前路由/当前页面”与“当前选中文档”解耦。
- 取消 `DocList -> 自动打开第一篇文档` 的隐式副作用，至少在用户明确处于 Dashboard 时不要抢焦点。
## 3. Medium

### M1. Cookie 提取逻辑用前缀匹配，存在误判与脆弱性
**证据**
- `apps/cli/src/server/auth/middleware.rs:77-88`
- `apps/cli/src/server/ws/mod.rs:121-132`
**问题**
- 当前逻辑是 `pair.strip_prefix("token")`，不是精确匹配 `token=...`。
- 若请求里出现 `token_csrf=...`、`token_backup=...` 这类 cookie，解析可能提前返回错误值，导致本来合法的登录态被拒绝。
**建议**
- 统一改用精确 Cookie 解析器，不要手写字符串切片。
- HTTP 和 WebSocket 握手共用一套提取函数，避免分叉。

### M2. 浏览器不提供 `localStorage` 时前端会直接 panic
**证据**
- `apps/web/src/hooks/use_core/mod.rs:42-48`
**问题**
- 当前代码直接 `expect("localStorage not available")`。
- 在 Safari 私密模式、某些嵌入式 WebView、严格隐私策略或未来 CSP 沙箱下，这会让前端启动即崩。
**建议**
- 身份状态应优雅降级到进程内存，而不是 `expect()`。
- 即便保留本地持久化，也要允许“无持久化”模式启动。

### M3. 协议说明、验收用例与代码现状已经系统性漂移
**证据**
- `deve-note plan/deve-note plan.md:5` 仍写着 `Ready for Implementation`
- `deve-note plan/05_network.md:38` 仍写“Client-Server 使用 JSON”
- `apps/cli/src/server/ws/send.rs:21-39`、`apps/web/src/api/connection.rs:109-147`、`apps/cli/src/server/ws/mod.rs:55-110` 已经是“二进制优先、JSON 降级”
- `deve-note plan/acceptance-cases/05_ui.md:41`、`deve-note plan/acceptance-cases/08_auth.md:28,37,46,64`、`deve-note plan/acceptance-cases/09_i18n.md:37`、`deve-note plan/acceptance-cases/12_tech_release.md:48-49` 仍大量使用 `3000` 和旧端点
- `apps/web/src/components/quick_open/mod.rs:5`、`apps/web/src/components/spectator_overlay.rs:5` 仍引用不存在的 `03_ui_architecture.md`
**问题**
- 文档入口把项目描述成“准备开始实现”，而代码其实已经处于中途演化状态。
- 验收用例仍围绕旧端口、旧路径、旧协议写，已经无法充当可靠回归基线。
**建议**
- 先把“主计划状态”“验收用例端口/端点”“协议格式说明”统一。
- 删除或替换失效引用，避免新协作者继续追错文档。
- 根目录补一个 `README`，现在仓库顶层没有项目入口说明。

### M4. 文件长度与模块边界仍明显偏离仓库铁律
**证据**
- `crates/core/src/tree/manager.rs` 289 行，已超过 250 行熔断阈值
- Rust 源文件统计: `>250` 为 1 个，`130-250` 为 96 个
- Plan 文档统计: `>250` 为 2 个，`130-250` 为 7 个
- `deve-note plan/08_ui_design_03_mobile.md` 273 行
- `deve-note plan/acceptance-cases/05_ui.md` 519 行
- JS Bridge 按仓库规则目标 `<200`，当前 `apps/web/js/extensions/hybrid.js` 为 228 行
**问题**
- 虽然多数文件还没越过 250 行硬限，但已经大面积长期处在“接近熔断”的状态。
- `tree/manager.rs` 已经实质违反仓库硬规则，说明结构治理没有跟上功能增长。
**建议**
- 优先拆 `tree/manager.rs`、同步 handlers、前端 `search_box` 与 `use_core` 大模块。
- Plan 文档同样要做模块化，不要只要求源码小文件化。

2. 再修 `H1` 和 `H2`，明确 Web 端到底是 Dashboard 还是 Peer，并打通 HTTPS/反代/登录闭环。
