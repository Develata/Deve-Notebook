## 2. High

### H1. WebSocket 提交主链路仍绕过三阶段提交实现，前端 Commit 与 HTTP Commit 语义分裂
**证据**
- 前端 Source Control 按钮走 WebSocket：`apps/web/src/hooks/use_core/callbacks_sc.rs:60-63`、`93-96`
- WebSocket 路由把 `Commit` / `CommitAndPush` 送到旧 handler：`apps/cli/src/server/ws/route/source_control.rs:32-45`
- 旧 WS handler 直接调用 `deve_core::ledger::source_control::create_commit(...)`：`apps/cli/src/server/handlers/source_control/commits.rs:19-27`、`107-115`
- 但真正实现“读工作区内容 -> diff 快照 -> 生成 Op -> 追加 Ledger”的新路径在 `RepoManager::commit_staged_with_ops*`：`crates/core/src/ledger/manager/commit_ops.rs:19-72`
- HTTP API 已经走新路径：`apps/cli/src/server/handlers/source_control/http.rs:113-120`、`123-130`

**问题**
- 当前仓库存在两套提交语义：
  - Web 前端实际使用的 WS 路径：旧实现，只写 snapshot/commit 记录。
  - HTTP / plugin-host 路径：新实现，才会从 staged working tree 生成 ledger ops。
- 这直接违背 `07_diff_logic.md` 与 `验收清单.md` 中的三阶段工作流要求。

**风险**
- Web UI 上点击 Commit 时，用户以为提交的是工作区文件，但运行时并没有稳定执行“stage -> diff -> append ops -> ledger_seq”。
- 同一 repo 中，HTTP 与 WS 客户端提交结果可能不同，造成审计、同步、历史回放语义分裂。

**建议**
- 把 WS `handle_commit` / `handle_commit_and_push` 统一切到 `RepoManager::commit_staged_in_local_repo(...)` 或等价 repo-scoped trait 路径。
- 删除旧的 snapshot-only 提交入口，避免运行时继续分叉。

### H2. Working Directory -> Staging 的运行时迁移仍未真正成立，`pending_fs_ops` 只被“隐藏”而不是被消费
**证据**
- 计划定义 `stage_pending` 语义：`crates/core/src/ledger/manager/source_control_ops.rs:150-166`
- 但 WS handler 暂存时调用的是 `stage_file`，不是 `stage_pending`：`apps/cli/src/server/handlers/source_control/staging.rs:21-23`、`73-78`
- HTTP API 同样调用 `stage_file_in_repo`：`apps/cli/src/server/handlers/source_control/http.rs:90-98`
- `ChangesList` 只是把已经 staged 的 path 从 pending 列表中过滤掉：`apps/cli/src/server/handlers/source_control/changes.rs:69-82`
- 即使走新 commit 路径，`commit_staged_with_ops_in_local_repo` 也只清 `staging`，不清 `pending_fs_ops`：`crates/core/src/ledger/manager/commit_ops.rs:59-64`

**问题**
- 当前的“Stage”更像是“给 path 打个 staged 标记”，而不是把它从 Working Directory 正式移入 Staging Area。
- `pending_fs_ops` 仍然保留原条目，UI 只是临时把它藏起来。

**风险**
- 提交后 `staging` 被清空，而 `pending_fs_ops` 仍在，变更会再次出现在 Changes 列表里，形成“幽灵未提交项”。
- 同一路径若在 stage 后继续修改，当前模型也无法正确表达“已暂存内容”和“新增未暂存内容”并存。

**建议**
- 对外入口统一改为 `stage_pending(_in_local_repo)`，让 `pending_fs_ops -> staged` 真正迁移。
- commit 成功后按 path 回收对应 pending 条目，而不是仅清空 `staging`。

## 3. Medium

### M1. 删除提交路径仍未向 Ledger 追加显式删除语义，删除传播依赖元数据副作用而非权威操作
**证据**
- 新提交路径对 `Deleted` 分支仅移除 snapshot：`crates/core/src/ledger/manager/commit_ops.rs:53-55`、`93-105`
- 本地文件删除时，Watcher 直接删 metadata/path mapping：`crates/core/src/sync/handler.rs:107-125`
- `delete_doc_in_local_repo` 只是 metadata 删除，不是 ledger op：`crates/core/src/ledger/manager/metadata_ops.rs:84-91`

**问题**
- 当前删除流程主要依赖 metadata/path mapping 的即时删除与 snapshot 清理，而不是 repo-scoped ledger delete op。
- 这与计划里“Commit 时对比 Ledger 快照生成 Ops”的契约仍不一致。

**风险**
- 删除语义难以稳定通过同步、审计和历史重放传播。
- 一旦后续路径恢复、快照恢复或远端补齐依赖 ledger 语义，删除操作可能表现不一致。

**建议**
- 为 staged delete 生成显式 tombstone/delete op，并让 commit 锚定该 op 的 `ledger_seq`。
- 把 metadata 删除从“权威写入”降级为“随 ledger delete op 派生更新”。

### M2. 认证状态只在启动时检查一次，Cookie 过期后的 Web 端仍会落入“无限重连遮罩”而不是回到登录页
**证据**
- `App` 只在启动时调用一次 `check_auth_status()`：`apps/web/src/app.rs:31-41`
- 连接管理器把 WS 打开失败与读取失败都当作普通断连处理：`apps/web/src/api/connection.rs:38-78`、`122-157`
- `DisconnectedOverlay` 不区分未认证与网络断连：`apps/web/src/components/disconnect_overlay.rs:12-25`
- 前端没有看到任何后续 `401 -> set_auth_state(Unauthenticated)` 的路径（全仓检索仅登录模块使用 `AuthState`）

**问题**
- 首次登录闭环已经有了，但“会话过期 / 服务器重启后 Cookie 失效 / 其他端登出”这类二次认证场景仍未收口。

**风险**
- 用户会看到持续的 “Reconnecting...” 遮罩，而不是明确的“需要重新登录”。
- 这会把认证故障误呈现为网络故障。

**建议**
- 把 HTTP 401 与 WS 握手失败接到统一的前端 auth state machine。
- 一旦 `/api/auth/me` 返回 401，或者 `/ws` 握手失败且后端返回 401，应切回 `AuthState::Unauthenticated`。

### M4. `pending_fs::content_hash` 的实现与契约不一致，冲突检测与 watcher 去抖实际只建立在 64-bit 哈希上
**证据**
- 注释声称“SHA-256 哈希前缀，16 字节 hex 编码”：`crates/core/src/source_control/pending_fs.rs:28`、`116-123`
- 实现实际使用 `DefaultHasher`，输出 `{:016x}`，即 64-bit 摘要：`crates/core/src/source_control/pending_fs.rs:119-123`
- 该值被用于冲突检测与自写回 watcher 忽略：  
  `crates/core/src/source_control/conflict.rs:22-50`  
  `crates/core/src/sync/persist_guard.rs:32-77`

**问题**
- 当前不是文档说的 SHA-256，也不是 16-byte 前缀；运行时碰撞裕量比设计意图小很多。

**建议**
- 若追求低成本，可改为 `blake3` 截断 128-bit；若追求契约一致，则改成真正的 SHA-256 前 16 字节。
- 至少先修正文档与类型注释，避免后续开发者基于错误假设继续扩展。

## 5. 具体优化建议

### 5.1 先统一 Source Control 入口，再谈 UI 优化
- **最优解**：所有外部入口（WS / HTTP / plugin host）统一调用同一套 repo-scoped `stage_pending -> commit_staged` 服务层。
- **当前朴素做法**：不同入口各自调用不同 helper，导致 HTTP 与 WS 提交语义分裂。
- **底层原因**：
  - 最优解把“工作区 -> 暂存 -> ledger”抽成单一路径，状态机唯一，审计点单一。
  - 朴素做法会在多个入口重复拼装流程，最终一定出现某个入口仍停在旧实现。

### 5.2 用类型而不是注释维护 repo-scoped 不变量
- 为 `SessionBoundRepo`、`LocalRepoScope`、`ReadonlyRemoteScope` 引入轻量包装类型，避免裸 `RepoId + Option<PeerId>` 在 handler 间到处流动。
- 这样做的收益不是“代码更漂亮”，而是能把：
  - “远程分支禁止本地 Source Control 写入”
  - “同步消息必须命中已绑定 repo”
  - “Tree/Broadcast 只能投递给当前 repo”
  这些约束前移到类型层。

### 5.3 把 `pending_fs_ops` 变成真正的状态迁移表
- 现在更像“两张表 + 前端过滤”。
- 应改成明确的状态迁移：
  1. `pending_fs_ops` 记录 Working Directory
  2. `stage_pending` 原子迁移到 staged
  3. `commit_staged` 原子迁移到 ledger + clear pending/staging
- 这是比“前端收到 `StageAck` 后刷新列表”更优的做法，因为状态一致性在后端原子事务里闭环，前端只消费结果。

### 5.4 对 watcher / conflict 的内容哈希做一次低成本升级
- 若继续用 64-bit `DefaultHasher`，CPU 便宜，但契约不准，碰撞裕量也偏低。
- 更平衡的方案是 `blake3` 截断 128-bit：
  - 相比完整 SHA-256 更轻。
  - 相比 `DefaultHasher` 更接近“内容指纹”的工程语义。
  - 对 CPU cache 友好，且实现简单。

### 5.5 文档治理应从“手工修”升级为“可验证”
- 建议把以下值提取成单一真值源，并让验收文档通过生成脚本消费：
  - 默认端口
  - 认证端点
  - 关键环境变量名
  - `report` 中引用的设计文档路径
- 否则每次重构后，代码先变，`acceptance-cases` 永远滞后半步。

## 6. 建议优先级
1. 先修 `H1 + H2`：统一 WS/HTTP 的 Stage/Commit 主链路，真正落地三阶段工作流。
2. 再修 `M1`：给删除提交补上显式 ledger 语义，避免同步与历史回放继续建立在 metadata 副作用上。
3. 接着修 `M2`：把“会话失效”从“断网”里剥离出来，补齐 auth state machine。
4. 最后处理 `M3 + M4`：清理验收漂移，并把内容哈希契约改成实现一致。
